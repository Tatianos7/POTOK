# Weighted admitted worker assembly

`createWeightedAdmittedGenerationWorkerV1` connects actual weighted selection and per-slot decision projection to the existing request load → independent validation → record → activation protocol. It takes explicit preparation and warning sources, optimization policy/metrics, admitted authority SQL session and gateway. `comparison` must be `STRICT` or `ROBUST_CONVENIENCE_BOUNDS`; no failure changes modes or falls back to first-feasible selection. Existing factories keep their defaults.

The worker creates `createWeekDecisionProjectionPortV1` internally, so no caller-provided decision trace is needed. All slots reference the actual whole-week optimization result. The existing worker binding verifies canonical loaded input/manifest bytes, constructs the graph and checks the exact proposal against independently loaded authority twice: during proposal generation and immediately before recording. Only the admitted SQL reader is used; no owner-reader fallback exists.

The runtime gate is false by default. Preparation, warning lookup, metric assessment, authority SQL and allowed gateway calls are guarded before and after their asynchronous boundary. Losing the gate after a database commit is an uncertain reply, not a rollback: after reopening, the existing request status resumes without generating or recording twice. Missing metrics in strict mode, unavailable/revoked final authority or conflicting record state stop acceptance. Unknown yield and served grams remain null; generating a PLAN creates no FACT.

Configuration strings, mode and dependency references are captured at assembly. Callers remain trusted backend implementations and must independently admit/pin source and policy data. This module does not create connections, roles, authority receipts, source rows, database schema, routes or runtime flags. It does not install the slot projection audit receipts into a new persistence store; Graph persistence carries the actual optimization/candidate references through the existing protocol.

## Verification boundaries

Nine new tests run real metric calculation, weighted search, decision projection, graph construction, both independent validators and the existing record/activation state machine. The recorded bytes are read using the real client readback decoder/service and opened by the existing menu-entry controller. Tests cover strict-known success, strict-unknown rejection, default and mid-flight gate closure, final authority revocation, loaded-input substitution, record conflict, lost replies, recovery and clearing a stopped menu. Their source/admission/SQL/gateway/Auth responses are explicit synthetic fixtures; this is not a deployed app or real-user test.

The native preparation suite additionally loads actual PostgreSQL request-only context, calculates metrics with unknown convenience, generates real weighted decisions, publishes an explicitly synthetic proposal-bound warning fixture, and passes both independent authority checks through the actual admitted SQL reader before exact-byte gateway recording. The gateway remains synthetic in that scenario; existing native storage/readback suites independently cover their SQL contracts. No live Supabase mutation or deployment is performed.

Remaining deployment work includes assembling/reviewing the draft dependency stack, actual admitted catalog/policy/warning sources, approved installation of required Staging packages, and an authenticated Staging request → stored menu test before a separately approved activation. Cooking and recipe refinement remain deferred; missing factual values are not fabricated.
