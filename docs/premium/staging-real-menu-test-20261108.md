# POTOK — реальные рецепты на существующем тестовом экране

Экран: `/staging-generator-check.html` существующего проекта `potok-staging-test`.
Новый основной блок: «Собрать неделю из реальных рецептов». Старые диагностические
блоки сохранены под «Технические проверки».

Пользователь входит как раньше, выбирает 1400/1600/1800/2000 ккал и дату, нажимает
«Сгенерировать неделю из рецептов». Сервер повторно проверяет настоящий Auth через
GET `/auth/v1/user`, читает закреплённый приватный справочный каталог, запускает
тот же существующий bounded authoring selector и возвращает семь дней с карточками
только выбранных рецептов. Никаких файлов или APK на телефоне не требуется.

Это тест по реальным исходным рецептам, а не утверждённый персональный план.
Источник: 132 рецепта, 122 с полными справочными числовыми входами. КБЖУ, аллергены,
состояния ингредиентов и практические порции не становятся проверенными. Ужин
тестово использует LUNCH. Исходные количества, состояния и инструкции сохранены;
дополнительные авторские notes явно исключены из проекции. Неизвестные массы
остаются неизвестными. Для 2000 ккал текущая выборка возвращает пустой результат,
не ослабляя ограничения и не объявляя весь каталог непригодным.

## Границы и публикация

Новая функция `/api/staging-real-week` разрешена только при `VERCEL_ENV=preview`,
точном Staging Supabase origin и отдельном флаге. Единственный внешний запрос
функции — проверка Auth GET. RPC, запись в БД/дневник/план, выдача approval,
публикация рецептов и trusted worker не вызываются. Ответ не кешируется.

Каталог не коммитится в открытый репозиторий и не кладётся в публичные ассеты.
На сервере проверяются SHA-256 проекции и исходного workbook. Brotli распаковка
ограничена 2 МБ. Сервер возвращает только выбранные рецепты после проверки входа.

Подготовленные параметры только для preview-ветки
`codex/staging-real-menu-test-20261108` в существующем тестовом Vercel-проекте:

- `POTOK_STAGING_REFERENCE_TEST_ENABLED=true`.
- `POTOK_STAGING_REFERENCE_CATALOG_BR64`: зашифрованный приватный каталог, 54184 байта.

Запись этих параметров автоматически отклонена; повторное чтение подтвердило
их отсутствие. Публикация на существующем тестовом адресе ещё не выполнена.
Нужно отдельное согласование владельца на эти параметры и обновление существующего
тестового сайта. Production и Supabase не изменены.

## Проверки

- 17 тестов HTTP/Auth/сценариев/границ клиента и существующего viewer — PASS, без SKIP.
- Локальный HTTP handler + реальный каталог + собранный браузерный интерфейс:
  360/393/430 px × четыре цели — 12 сценариев PASS; реальные рецепты открываются
  во всех семи днях. Для 2000 — ожидаемый пустой результат.
- Устаревший ответ после смены цели не появляется; отказ Auth очищает меню;
  анонимный запрос получает 401. 19 API-вызовов; только 18 Auth GET на тестовый порт.
- Auth в локальной browser acceptance — явно синтетическая фикстура, не hosted E2E.
- TypeScript, lint изменённых модулей, Vite staging build и проверка свежести
  сгенерированного API выполняются перед публикацией. Hosted Auth с сессией
  владельца и ручной тест на телефоне ещё не выполнены.

Воспроизводимый приватный вход:

```bash
node scripts/prepare-staging-reference-catalog.mjs /private/catalog.json /private/catalog.br64
node scripts/build-staging-real-week-api.mjs --check
node --import tsx --test src/server/__tests__/stagingRealWeekApiV1.test.ts src/dev/__tests__/authoringWeekViewer.test.tsx
node scripts/acceptance/staging-real-menu-browser.mjs /private/catalog.br64
```

API — автоматически собранный ESM-модуль из исходных TypeScript-модулей.
Изменение source требует `node scripts/build-staging-real-week-api.mjs`; CI
проверяет точное совпадение. Сам приватный каталог в этот артефакт не включается.
