# Inactive meal → day → week proposal assembly

`createGenerationDayOptionsV1` connects the catalog meal preparer to deterministic day enumeration and the existing bounded week search. The only preparation input is a canonical request UUID, plus optional primitive raw computation budgets. It loads the trusted preparation source once per invocation, passes those exact bytes to the existing meal preparer, and reuses the pinned input, manifest, preferences, safety, distribution and policy bodies. It does not accept caller-supplied meal objects or day validity flags.

`generate(requestOperationId, limitsRaw)` accepts exactly `maxDayEvaluations` and `maxWeekEvaluations`, each an integer from 1 to 1024; both default to 1024. These are work bounds, not dietary rules. If the known day Cartesian pool exceeds its budget, it returns `DAY_SEARCH_LIMIT_REACHED` before warning reads. If more than 16 valid day alternatives would exceed the existing weekly input interface, it returns `RESOURCE_LIMIT_REACHED` without truncating or silently ranking away alternatives.

For every actual prepared meal, the independent read-only warning port is called with request, slot, meal digest, validation evidence digest and policy digest. A null result means unavailable evidence. It never means five false signals. Non-null results retain their original bytes and must pass the preparation-only raw warning decoder. Corrupt, replayed, duplicate-key or non-raw warnings abort, rather than being treated as unsuitable meals.

The new `decodePreparedMealWarningEvidenceRawV2` reuses the existing private warning entry verifier: same entry contract, digest, signals, policy/evidence/slot and recomputed meal-state binding. It admits one actual prepared meal without inventing a generated Graph or decision receipts. It additionally verifies slot/type/goal/composition bindings against the trusted preparation context. It does not attest the meal's complete catalog provenance or admit a plan; the preparer and V2 day checks cover catalog admission, and the final V1 full-plan warning-set checks remain mandatory and unchanged. No warning issuer, review flag, source receipt or set digest is synthesized.

Each complete combination of warned meals is projected into the existing day DTO from pinned distribution bounds, requirements, goal target and source evidence. Required nullable goal axes remain nullable; no extra nutrient targets are guessed. `validateDaySnapshotRawV2` applies the same V2 manifest/axes normalization and day traversal as the child of the existing full-week validator. This checks total day nutrition, repeats within a day, exact required slot coverage, meal constraints and warnings. The existing V1 day contract remains the subordinate DTO, as in the V2 weekly boundary. The V1 public decoder and its timezone domain are unchanged.

The V2 normalization traversal was mechanically extracted unchanged except for the source loop variable; it is shared by the standalone day and weekly APIs. Tests compare the standalone result with the actual existing weekly-child result, including subject digests and UTC. The warning export audit now explicitly includes the sixth raw-only function while retaining all old full-plan/set replay checks.

Only VALID/VALID_WITH_WARNINGS day alternatives enter the bounded week search. It reevaluates the selected whole week with the actual V2 validator, retaining cross-day recipe/family/ingredient and specialty/expensive limits. A feasible result contains the real weekly domain result, day diagnostics and the original selected warning-entry bytes sorted by slot ID. It is recursively frozen. It is neither an ACTIVE plan nor trusted acceptance or consumption.

Explicit unsuccessful results distinguish missing preparation sources, incomplete meal pools, resource/day/week search limits, missing warnings, blocked domain evidence, infeasible days and infeasible supplied week pools. If unknown warning alternatives remain, exhausted known alternatives cannot prove exhaustive weekly infeasibility; the result reports missing warning evidence. A feasible known week may still be proposed with diagnostics for other unavailable alternatives. No optimality or full-catalog completeness is claimed.

No cross-invocation cache, retry, currentness rebase, database write, Edge/UI connection, payment flow, deployment or activation is added. Source and warning ports still require independently admitted/current storage. Final publication must recheck currentness/entitlement and the existing full Graph, plan, warning-set and trusted validation contracts. Independent real catalog publication, measured yields, generation/optimization policy evidence and decision receipts remain prerequisites; tests use synthetic reviewed fixtures only.

Validation covers the connected path, byte-preserved warnings, total day targets across slots, within-day and cross-day repeats, missing/forged warning data, bounded enumeration, day-pool overflow, unknown alternatives, warning retention, deterministic fresh reads and V2/V1 compatibility regressions.
