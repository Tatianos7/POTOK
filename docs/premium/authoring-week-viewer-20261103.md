# Local authoring week viewer

The next step after PR296 is a separate local React viewer for its versioned JSON reports. Run `npm run dev` and open `/authoring-week-preview.html`. Choose a report generated with `recipe-authoring-week-preview-v1.ts`. No source recipes or private report contents are committed.

This HTML is intentionally absent from the production Rollup inputs. It does not import App, authentication, Supabase clients, the trusted generator, persistence or the diary. It displays only user-selected files held in component memory, without localStorage or an upload operation. Loading a new file clears the previous report immediately, including errors; asynchronous reads cannot replace a newer selection. The file limit is 2 MB.

The decoder requires the exact offline contract and non-publishable/non-activatable markers. It validates seven sequential dates and ordered slots for a successful week, numeric per-serving references, daily sums at the producer's three-decimal precision, repeat caps, and unverified whole portions with unknown measured grams. It rejects malformed reports rather than repairing them. This validation does not establish source authenticity, trusted-plan acceptance, dietary safety or actual measured yields. The displayed workbook hash is metadata from the report, not a cryptographic authenticity claim.

The viewer preserves all distinct no-week diagnostics, including the unsuccessful 2000-kcal evaluated shortlist. It does not relax targets or multiply/divide references by the recipe's declared total servings. Day tabs show recipe names, whole source portions, reference calories/macros/fiber, unconfirmed grams, the test category mapping and search limitations. Rendering file text uses React escaping.

This is a functional test harness using existing utility styles, not a new approved product screen or a design-token change. PLAN remains distinct from FACT. No hosted environment changes or generator activation are part of this step.

Validation: five contract/rendering tests, TypeScript, targeted ESLint and the full production build pass. Local Chromium loaded the actual private 1400/1600/1800 reports and switched through all 21 days with four cards each. The 2000 report displayed its no-day result; malformed JSON data cleared the previous menu. At 390 px the page had no horizontal overflow. No page errors or Auth/RPC/Supabase requests were observed. The production output contains neither this HTML entry nor the offline viewer code. These checks do not claim a hosted application or phone-device E2E.

## Recipe cards from the local authoring catalog

Load the JSON exported by `recipe-authoring-test-catalog-v1.ts` into the second file input (before or after the week report). The original 2 MB file bound also applies to the catalog. Each meal then offers an inline recipe expansion, linked by exact recipe ID and the same reported workbook SHA-256, name, declared servings and per-serving reference nutrients. Missing IDs, a different workbook hash, divergent reference data or BLOCKED status prevent opening that recipe. No name-based fallback is used. These are consistency checks on selected local files, not proof of authenticity or trusted source approval.

Ingredient quantities are displayed for the whole source recipe, explicitly distinguished from the one source portion assigned in the menu. Original amount/unit and recorded gram weight stay separate: unknown values remain unknown, optional items stay optional and ML/PCS are not converted to grams. Notes and preparation descriptions are retained as source text without inferring weighing state. Declared yield/servings are not presented as measured. Steps retain their source numbering, instruction, optional duration/temperature and notes, sorted by explicit order. Missing ingredient/step lists get an explicit missing-data message. Source text is escaped by React.

Replacing a catalog clears its old data immediately, including on malformed input; a sequence guard prevents an earlier asynchronous read from replacing the latest selection. Each day/meal identity owns its expansion so changing days does not retain an earlier recipe's open panel. Catalog loads do not change the week or its nutrition totals. No writes, source publication, runtime activation or consumption records are introduced.

Recipe-card validation: the expanded suite has 10 passing contract/rendering tests, including exact linkage, inconsistent catalogs, duplicate/orphan rows, missing quantities, no portion scaling and HTML escaping. All 132 actual catalog recipes decode; 84 meal references across the three actual weeks match. Chromium opened all 84 cards and checked every displayed ingredient name/instruction and child counts (400 ingredient appearances and 380 step appearances, including repeated recipes). At 390 px there was no horizontal overflow. Invalid catalog replacement cleared expansions, another source hash blocked them, and the 2000 no-week result retained no recipe cards. No page errors or Supabase/Auth/RPC requests were observed. These remain local authoring tests, not hosted application acceptance.

## Selection directly into the viewer

The primary flow now takes only the authoring catalog file: select a technical target (1400/1600/1800/2000), an explicit week start and click the offline selection button. The resulting report crosses the existing viewer decoder and immediately exposes day/recipe views. Importing a previously saved week report remains available under a separate disclosure. No report JSON file is needed for a new selection.

The original CLI algorithm was moved to `src/dev/authoringWeekSearchV1.ts`, with the same ordering, arithmetic, category mapping, shortlist policy, repeat cap, limits and diagnostics. The CLI imports/re-exports that implementation and retains its workbook I/O wrapper. The browser imports no Node, XLSX, database, auth or trusted runtime module. Its catalog projection uses validated identity, declared portions, per-serving references, eligibility flag and primary category. It does not promote a false eligibility flag or impute missing nutrients.

Scenario controls use the existing explicit example settings: four whole source portions per day, ±10% calorie tolerance, at most two uses per recipe per week, LUNCH-as-evening test assumption, 12 ranked candidates per slot, four per daily slot, four retained day options, 256 day and 1024 week evaluations. These are fixed technical experiments, not dietary prescriptions or production generation settings. A no-week result never triggers automatic target/portion/tolerance changes.

Changing target/date clears the previous report immediately. Replacing the catalog clears a report produced by local selection, including on a load error; saved-file reports keep their previous source mismatch checks. A new selection invalidates pending saved-report reads. The selection button is unavailable while no valid catalog/date is present or the catalog is loading. Output stays in memory; it creates no stored plan or FACT.

Validation: 17 focused tests pass (12 viewer/selection and 5 existing producer tests), plus TypeScript and targeted ESLint. The entire new producer output on the actual catalog deep-equals the PR298 producer output for all four targets, including diagnostics and no-week status; the decoded browser projection also matches. This verifies the extraction without committing private catalog/report contents.

The production build/postbuild passes and still excludes the local viewer. Chromium exercised real catalog → select → day → recipe without selecting any week JSON: all 84 cards across the three successful scenarios matched the producer's recipe names. It also verified the 2000 no-week result, changing the week start, clearing a generated week on scenario/catalog change, disabling selection after invalid catalog input, no 390 px overflow, no page errors and no Supabase/Auth/RPC requests. This is a local browser flow, not the hosted Staging request/worker/persistence/Auth scenario, which remains outstanding.
