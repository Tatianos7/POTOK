# Generation validation storage — disposable candidate v1

Status: **DISPOSABLE SQL CANDIDATE / NO LIVE INSTALLATION OR ISSUANCE**.
Base: #246, `8fa78b7eb879638f3d564b0e18deccc108280526`.

## Implemented scope

Two private append-only stores hold existing raw policy/validation evidence for
one durable request and independently supplied warning evidence for one exact
proposal SHA. They do not duplicate request, manifest, preference or safety
storage. Their raw UTF-8 storage checksums are generated by PostgreSQL; existing
typed content/evidence digest domains remain unchanged.

The candidate checks request/account/typed-input binding, warning-to-input/policy
digest references and duplicate JSON before persistence. Both insert paths acquire
a SHARE row lock on the durable request before checking its status, serializing
insertion against a terminal status transition. This narrow fence does not cover
account closure, Auth or entitlement. A primary key prevents
replacing an already stored request/proposal package. There is no automatic
conflict-ignore API, upsert, rewrite, deletion, cleanup or publication RPC.
UPDATE/DELETE/TRUNCATE fail, including ordinary owner statements against existing
records. Request references use RESTRICT, never cascading removal of history.
RLS and FORCE RLS are enabled; table/function access is revoked from PUBLIC,
anon, authenticated and service_role. No application policy or grant is added.

`read_generation_validation_source_v1` performs one STABLE SELECT without locks,
attempt insertion or status changes. It assembles the exact source wrapper used
by #246 from pinned stored bytes plus the new raw evidence stores. It requires
matching current manifest/preference/safety/policy heads and a REQUESTED or
GENERATING request. Missing data, wrong proposal or stale inspected heads returns
NULL. The explicit SQL driver uses two bound parameters, admits exactly one
string/null result and neither retries nor silently accepts malformed results.

The reader has SECURITY INVOKER, fixed search_path, no application EXECUTE and an
owner-session sentinel. That sentinel is a **disposable nondeployment boundary**,
not a design for running the application with postgres credentials. No connection
or credential is included in the driver and it is not wired into Edge/app runtime.

## Explicit limits before any operational use

This is persistence/consistent source-read acceptance, not full generation
authorization. The reader does not verify user JWT/session, effective Premium,
current Goal/selection/entitlement lineage, receipt provenance or account closure.
The inspected head checks do not replace the existing full currentness gate or
the final write transaction's entitlement/CAS checks. A read snapshot may be stale
by the time it is consumed; repeatable-read consistency does not grant permission
to activate after an authority change.

Raw source receipt references record supplied provenance links but cannot
authenticate themselves. Only strict existing TypeScript domain validation can
establish the tested content bindings; table checks alone do not perform the
full policy/recipe/warning semantics. A compromised privileged writer can supply
self-consistent false assertions. No reviewer authentication, evidence issuer,
signature or source approval is implemented by storing text.

Retention/account closure/erasure treatment of these account-linked immutable
records is still unresolved. RESTRICT is a history-preservation choice for this
prototype, not a completed deletion policy. No live installation is permitted
until those decisions, independently verified issuance and a narrow protected
backend reader identity are reviewed and tested. Never pass postgres credentials
to Edge or enable application access to bypass missing reader authorization.

## Executable boundaries and test environment

The SQL file is intentionally **not a migration**. Before its first DDL it requires
the fixed `potok_generation_store_disposable` database, UTF8, postgres session
and explicit disposable marker. Callers install it inside a transaction. The
guard remains intact; do not remove it to run this test package on Staging or
Production. A later deployment artifact must be separately prepared/reviewed.

The dedicated workflow provisions a clean PostgreSQL 17.6 service on loopback
using synthetic credentials/data only. The test harness accepts no remote URL
or arbitrary host/database. Real original fixture fields are produced by the
existing TypeScript encoders; base request/authority tables are **minimal synthetic
fixtures**, not a full Supabase restore or the real issuer/Auth/RLS chain.

Tests execute the unmodified guarded SQL candidate, store synthetic packages,
read them through the SQL driver -> #246 loader -> #245 actual week validator,
verify read-only behavior and account/proposal/head binding, deny application
roles including a BYPASSRLS service_role, prohibit history rewrites/cascades,
reject duplicate warning JSON and exercise two independent connections around a
head change, plus actual insertion racing a terminal request transition. The
observed consistent old snapshot is explicitly not proof of
fresh authorization at commit. Wrong-database and missing-marker attempts fail
before new DDL. No test uses a connected Supabase project.

Locally the SQL driver/pure suites run; the native suite explicitly skips unless
its fixed disposable CI environment is enabled. Report native acceptance only
after the dedicated PostgreSQL job passes, never from that local skip.
