# Private OTP and A/B profile acceptance

Continuation of owner-provided PRIVATE_AUTH_READY_OK for #214. The fixed-target command --run-private-auth-ab creates two random synthetic example.test identities through real local Auth OTP, verifies the returned tokens through Auth /user and PostgREST, and checks own/foreign/protected-profile behavior. It does not prove full application/browser, workout/food/program/media paths, real payments, hosted exposure parity or a production release.

## Scope and original-data proof

The script requires the same isolated candidate/baseline and existing API/Auth identities, successful twelve-candidate receipt, original backup hashes, eight unchanged source dependencies, runtime cron/listener/data-directory guards and all original final security contracts. It records sorted per-row full JSON SHA-256 multisets privately for all 112 original tables. After testing every original hash multiplicity must remain present. Same-count historical edits/deletes fail; new rows are allowed only in the explicit Auth lifecycle tables and public.user_profiles. Exactly two Auth users and two profiles must have been added for success. Auth schema definitions and final effective security/source contracts are checked again, authority remains empty, and all original backups remain byte-identical. Sequence counters may advance through normal Auth inserts; they are not reset.

This intentionally adds test data, so later raw row totals need not equal 14888. It is not a baseline rollback or an excuse to ignore original row changes. The private original-row multiset is the preservation reference for follow-up tests. The copied original baseline is untouched. Existing bootstrap/installation runners must not be blindly repeated after these deliberate additions.

## Local-only mail and real identity

An ephemeral credential-free Node worker shares the captured network-none namespace. It opens a loopback-only SMTP capture on 11025 and a template endpoint on 13003; recreated Auth listens on 13002. Before stopping the old Auth, the controller checks that these ports are outside the namespace's actual ephemeral TCP range. This avoids the bind collision observed at the earlier high Auth port in CI. It accepts only its two generated synthetic recipients, caps input sizes, implements the narrow SMTP protocol required by Auth, and extracts real six-digit GoTrue tokens into memory. The HTTP template returns only a GoTrue placeholder, never a received token. It neither relays mail nor exposes a code endpoint. No master JWT key, database credential, Docker socket or volume is passed to the worker. Actual Auth OTP issuance/verification supplies its user JWTs; tokens are not forged or printed.

The current Auth process must be recreated to use the local token template. Before any stop/rename the controller records its captured identity and a stopped-backup name. It stops and preserves the prior Auth container, starts the local worker, and creates the new fixed-name Auth with the same image/namespace/key/role/disabled workers and explicit serve. Only the controlled loopback Auth/site port settings and confirmation/magic-link template URLs change. Database/API containers and volumes are not stopped or recreated. State checkpoints are updated after each captured container ID. No automatic unsafe restore/delete runs on failure; a stopped attempt is diagnosed from local checkpoints and must not be repeated.

Both users request a real email OTP and verify it. Each creates a profile through the same minimal id_user API insert used by profileService, updates its first_name, sees exactly its own profile, sees no foreign profile and cannot update the other profile. Attempts to write is_admin, has_premium, created_at or updated_at require 401/403 with 42501. Both verified admin/premium readers must return false; final stored profile flags remain false. No trusted grant/issuer or purchase mutation is called. This is direct HTTP acceptance; it is not a claim that the actual Login/Profile UI/service cache/account transitions were run on the full copy.

## Evidence and later use

Private-auth-ab-* (0700 / files 0600) contains original row hashes, generated test addresses, captured state/old Auth identity, private auth.env, worker-only recipient env, technical worker logs and a success result with synthetic IDs. Inspect/credential output is redacted. OTP/JWT values stay only in worker/Auth memory; no response bodies or original row values are logged. Do not upload or paste this directory. The worker stops after testing. The synthetic users/profiles and new Auth configuration remain for subsequent UI tests; SMTP/template capture must be supplied again for later logins. Cleanup is a separate scoped step using captured synthetic IDs, not a blanket delete of Auth or public tables.

PRIVATE_AUTH_AB_OK requires complete worker success plus unchanged original rows/schema/security. PRIVATE_AB_ORIGINAL_ROWS_OK alone is only the separate data check and is not OTP success. Failures may leave partial synthetic identities or renamed/stopped Auth; preserve evidence and the unchanged original baseline. Never send code/token/env files in chat.

## Validation

Seven local unit cases cover duplicate-preserving original-row comparison, same-count tamper/unrelated new-row rejection, exact template-only overrides, pinned credential-free worker arguments, fragmented/quoted-printable SMTP delivery, rejection of unrelated recipients and absence of code disclosure from the HTTP template. The CI-only fixture explicitly migrates a fresh disposable Auth schema, supplies a minimal RLS/column-grant profile table and a false-capability stub, and runs the same real OTP worker with Auth v2.197.0/PostgREST 16.5/Node. CI uses the maintainer's Docker Hub supabase/gotrue:v2.197.0 mirror to avoid ECR public shared-runner download limits, then captures its immutable local ID; owner runtime retains its already verified local ECR image. This proves the mail/token/profile protocol on a minimal synthetic fixture; only the owner run exercises actual full-copy functions/constraints. Native OTP CI must pass on the published head before the owner command is issued.

The duplicate legacy combined API run on #214 failed with PGRST204 while its stage label still named the earlier history loop. The actual exception came from an expected-success operation after that loop, not the strict denial helper. GET-column readiness can precede the cache used to resolve PATCH fields. This change uses a bounded zero-row execution_reason PATCH to wait for the actual write cache, updates the stage label before status/reason writes, and adds bounded synthetic-schema diagnostics. It never accepts PGRST204 as a permission pass or relaxes a denial assertion. Exact-head real API CI remains the validation gate for that fixture fix; current private Auth readiness remains owner-confirmed and no full app pass is inferred.
