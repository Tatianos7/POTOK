# Накопленные исправления: совместная проверка и порядок внедрения

Решение владельца от 26 октября 2026: текущий этап — безопасность; после его завершения обещанный фейерверк, затем продолжение генерации планов питания. Настоящие платёжные квитанции — отдельная последующая задача [#198](https://github.com/Tatianos7/POTOK/issues/198). Покупки пока не проверяются у провайдера. Не считать legacy billing events доказательством оплаты. Ни платежи, ни генератор этим пакетом не включаются.

## Статус и границы

Это интеграционная проверка и план допуска, **не разрешение на внедрение**. Текущие кандидаты — Draft; Production/Staging не изменены. Успех синтетической CI-проверки не заменяет испытание всей восстановленной схемы или приёмку приложения на ней. Mac для этой CI-работы не нужен; для полного приватного восстановления подойдёт компьютер с Docker любой поддерживаемой ОС.

Единственный источник порядка и SHA-256 входов — `scripts/security/accumulated/inputs.mjs`. Четыре внешних публичных файла загружаются по неизменяемому commit и проверяются по SHA-256; три файла текущей ветки проверяются по зафиксированным SHA-256. Несовпадение останавливает тест. Отдельной команды применения к hosted-проектам нет. У SQL снимается только один проверенный внешний transaction wrapper; вся последовательность испытывается внутри общей транзакции обычным `postgres` без superuser.

## Что именно проверяет общая репетиция

В одной синтетической схеме совмещены 17-колоночный профиль с тремя owner policies, исторические фото-миграции, финансовая схема, реальные публичные тела admin RPC/review policies и старого recompute, pg_trgm и GIN-индекс. Восемь старых RPC присутствуют; `rls_auto_enable()` — безвредная заглушка (event-trigger поведение не моделируется). Нормализация и базовые food/diary таблицы синтетические. Для положительного admin-сценария используются три неизменённых reader-функции v2 и упрощённая приватная fixture-таблица attestation, **не полный issuer/retention/lineage контракт**. Отдельный сценарий выполняется без verified infrastructure и требует отказа в администрировании.

Восемь сценариев: общий ROLLBACK с восстановлением содержимого всех синтетических public/control/storage таблиц и metadata; COMMIT с повторной проверкой итоговых прав вне транзакции; совместные реальные SQL-пути профиля/finance/admin/photo и неизменность дневника; обычные операции при отсутствующей authority; ошибка последнего кандидата с атомарным откатом предыдущих; неверный порядок с отказом и откатом; поздняя регрессия GRANT, обнаруженная общим verifier; отказ повторного применения одноразовых кандидатов без изменения защищённого состояния. Metadata включает отношения, колонки/ACL, функции, policies, defaults, constraints, extension и роли.

Ранний anonymous-кандидат проверяет сохранение тогдашних authenticated/service grants и SECURITY DEFINER. Эти проверки верны **сразу после него**, но не являются финальным контрактом: finance/catalog намеренно сужают права, а recompute становится всегда запрещающим SECURITY INVOKER. Поэтому anonymous containment идёт раньше; финальный verifier проверяет уже новые права и не требует возврата старых. Поздний повтор старого anonymous-кандидата после catalog должен остановиться. Повторная установка всей группы не обещается: source guards finance/catalog требуют исходные тела.

Итоговые условия: анонимный EXECUTE старых RPC отсутствует; клиент не получает TRUNCATE и записи защищённых колонок/finance; собственное entitlement-чтение доступно authenticated, недоступно service_role; клиентские purchase RPC закрыты, существующее серверное логирование остаётся; admin RPC недоступны service_role и требуют verified admin для authenticated; recompute закрыт даже владельцу по телу функции; фотографии и обычный профиль работают; pg_trgm находится в extensions. Две fixture default TRUNCATE записи другого владельца остаются видимым остатком, а не выдаются за исправленные.

Отдельные реальные OTP/Auth/PostgREST проверки есть в #195–197; actual-service импорт проверяется тестом #197. Они ещё не доказывают **совместное** поведение всех семи изменений через API/UI на полной схеме. Тест настоящих платёжных квитанций отсутствует и отложен в #198. Приватные hosted definitions, ACL snapshots, пользовательские записи и резервная копия не входят в этот пакет.

## Порядок подготовки выпуска

1. Зафиксировать эту комбинацию и CI exact HEAD. Не менять pinned SQL незаметно. Проверить diff выбранной release-ветки относительно master; включить из #197 только нужное изменение импортёра до отключения recompute. Остальная account-isolation правка #186 требует отдельного решения и теста, она не входит в эти семь SQL.
2. Завершить read-only проверку authority: существующий verified predicate, владелец/права, приватное хранилище, issuer, временные границы/отзыв, retention и учётные записи администраторов. Не переносить старые is_admin/has_premium как доказательство. Не устанавливать модель и не выдавать admin для прохождения теста. Если инфраструктуры нет, catalog намеренно оставляет admin закрытым; владелец должен отдельно принять это поведение либо одобрить проверенный prerequisite-пакет. Staging v2.1 и неприменённый v2.2 repair не означают готовность Production.
3. Провести read-only drift/compatibility проверку точной цели: PG, owners, RLS, сигнатуры/тела, profile shape, существующие grants, classification личных/общих foods и aliases, caller inventory. Несовпадение — остановка, не ослабление guards. Staging с отсутствующими legacy RPC не заполнять искусственно ради зелёного теста.
4. Подтвердить свежую приватную резервную копию и доступный пароль, восстановление на полной схеме, затем общую rollback-репетицию **этой семёрки**, persistent commit на отдельной восстановленной копии и фактические API/UI пути с A/B аккаунтами. Ранее успешная полная репетиция четырёх кандидатов не покрывает добавленные три. Не публиковать данные в CI.
5. Завершить требования письма Supabase: реестр новых public-объектов/явных GRANT/RLS, bootstrap/draft/sequence/view/function случаев и клиента. Исправление фото-таблиц не равно полному replay всех будущих объектов. Остатки default ACL другого владельца — отдельный platform/owner вопрос, без эскалации через hosted SQL.
6. После прохождения gates подготовить **отдельно рассматриваемый forward migration/release** с точным порядком выше, locks/timeouts, проверками до/после, финальными effective permissions и неизменностью данных. SQL `rehearsal.sql` с ROLLBACK для pg_trgm не является готовой миграцией. Не менять terminator на COMMIT на рабочей базе вручную. Предварительная клиентская версия должна убрать вызов bulk recompute, чтобы запрет RPC не ломал импорт.
7. Получить отдельное одобрение владельца на exact Production batch и окно. Выполнить только одобренную группу, проверить committed состояние через отдельное соединение и фактическое приложение. Наблюдать 42501/ошибки RPC, профиль/вход, фото upsert, чтение Premium, обычные личные продукты и admin, запрет чужих данных и неизменность истории. Зафиксировать acceptance без пользовательских данных/секретов.

## Остановка и восстановление

При ошибке до COMMIT вся общая транзакция откатывается. При неоднозначном результате COMMIT сначала read-only сверка exact состояния, без слепого повтора. После подтверждённого COMMIT не использовать старые unsafe down scripts: возврат клиентского TRUNCATE, profile/finance writes или старого recompute недопустим как обычный rollback. Отдельно подготовить и проверить безопасный forward repair, совместимую клиентскую версию и аварийный recovery из приватной копии при необходимости. Конкретные команды восстановления зависят от финального release и требуют проверки, здесь их нет.

**Текущий вывод: совместная синтетическая проверка подготовлена; Production release NO-GO до закрытия перечисленных gates.** Ни фейерверк, ни переход к генерации не означают, что эти проверки можно пропустить. После закрытия согласованного этапа следующий рабочий фокус — генерация планов питания, а не платёжный провайдер.
