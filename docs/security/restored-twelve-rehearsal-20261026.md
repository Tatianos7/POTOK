# Полная локальная копия: репетиция двенадцати кандидатов

26 октября владелец предоставил успешный вывод `EIGHT_RESTORED_REHEARSAL_OK` для исходных восьми кандидатов на приватной локальной копии: 112 таблиц / 14888 строк, сверка содержимого и возврата metadata после ROLLBACK. Это подтверждение со стороны владельца, не независимый доступ к его backup. Две other-owner default TRUNCATE записи остаются отдельным платформенным ограничением. Этот результат не включает #206–209.

Следующий инструмент — `scripts/security/accumulated/restored-twelve.mjs`. Он использует неизменённые `restored.mjs`, `inputs.mjs`, `checks.mjs` из #202, проверяя их SHA-256. Исходные восемь pinned SQL входов сохранены. После них в той же транзакции добавляются четыре always-ROLLBACK review-кандидата: paywall #206, explanation projection #207 и history #208 из exact public commit `2e84692a3b86315b4824ba176ec48b6d808266f6`, legacy quarantine #209 с узким уточнением day_date из отдельного pinned source, указанного ниже. SHA-256 всех четырёх проверяются до SQL; source guards не ослабляются. Снимаются только проверенные внешние transaction wrappers. Результат всегда содержит один BEGIN и один ROLLBACK, без COMMIT.

## Сохранность данных и откат

Контейнер, локальный Docker endpoint, actor, PG17, backup hashes, имя исходной папки и распределение 112 COPY / 14888 строк проверяются как в первоначальном runner. Используется захваченный container ID. Скрипт не принимает hosted URL, не делает login/link, не выдаёт authority и не активирует Graph/Edge/генератор. SQL выводит технический статус, не выгружает личные строки или hosted function definitions.

Для всех старых колонок сохраняется полная SHA-256 проверка содержимого, включая дубликаты, до/во время/после. Единственное исключение формы строки — новая nullable колонка `public.program_sessions.execution_reason`: при подсчёте хеша исключается только этот конкретный ключ только этой таблицы; во время установки отдельно проверяется, что во всех строках он NULL. Любое изменение старого plan_payload, status или другого поля обнаруживается. Наличие новой колонки до начала отклонит quarantine preflight. После ROLLBACK полная metadata сверка требует исходную структуру, включая отсутствие новой колонки.

В metadata снимки добавлена private namespace `potok_delivery`. Финально проверяются effective permissions восьмёрки, history/quarantine boundaries, права и exact source/owner/security/search_path projection функций, новый paywall и пустой authority ledger. Хеши backup проверяются повторно после успешного SQL.

Сценарий сохраняет сгенерированный SQL и публичную матрицу 12 входов в новую приватную локальную папку `twelve-rehearsal-*`. Backup файлы не перезаписывает. При SQL ошибке ON_ERROR_STOP закрывает psql и незавершённая транзакция откатывается; успех не объявляется. После ошибки проверять состояние, а не ослаблять guards, повышать роли или заменять ROLLBACK на COMMIT.

## Проверки самого инструмента

`restored-twelve.test.mjs` строит расширенную синтетическую fixture из публичной восьмёрки и phase-7 program schema, с двумя аккаунтами и историей. Отдельные protocol calls воспроизводят psql: TEMP-only prefix, одна candidate transaction с ROLLBACK, затем postchecks. Проверяются полный откат 12 кандидатов, подмена прежнего session payload при прежнем количестве строк, запись в новое reason поле, поздний GRANT на plan payload, подмена private projection reader, поздняя ошибка shape preflight и отсутствие входа/лишний transaction wrapper. Такие тесты не заменяют владельческий прогон 112 таблиц.

## Запуск владельцем и границы результата

Из исходной папки backup, с healthy `supabase_db_POTOK_BACKUP_2026-10-24`, выполнить Node 22+ на проверенный файл с единственным аргументом `--run-restored-local`. Portable вариант кладётся рядом с тремя уже проверенными файлами первоначального runner; перед запуском обязательно сверить опубликованный SHA-256 нового файла. Зависимости npm не нужны.

Успех требует `TWELVE_CHECKS_OK`, `TWELVE_ROLLBACK_OK`, `TWELVE_RESTORED_REHEARSAL_OK` и exit 0. Подготовка/CI сами по себе не означают, что это уже выполнено на копии владельца.

Даже успешная репетиция не означает release approval или persistent API/UI acceptance полной схемы. Остались default ACL платформенного владельца, проверка применения на отдельной постоянной тестовой копии и приложения, актуальный read-only drift, exact release scope, совместимый клиент, recovery/monitoring и разрешение конкретного выпуска. Quarantine намеренно отключает старую генерацию для всех тарифов, включая Free, после её выпуска; это решение должно быть явно рассмотрено, а не скрыто успехом SQL. Платёжные квитанции остаются последующей задачей #198; генерация продолжается после согласованного security milestone.

## Уточнение совместимости session schema

Первый владельческий прогон двенадцати кандидатов остановился на quarantine shape guard; успех всей группы не подтверждён. Обновлён только quarantine input: узкая авторская совместимость с завершающим `day_date date`, который уже читается публичным Progress-клиентом. Его точный источник — `90571af942a98b3822ed175ec1483a65adb5d8d7`; другие три follow-up и исходные восемь pins не менялись. Эта правка не удаляет/заполняет/синхронизирует поле и не выдаёт на него клиентскую запись. Миграция происхождения поля в репозитории не найдена, поэтому это не объявляется replay полной production schema.

Десять protocol cases включают обычную семиколоночную схему, восьмиколоночный вариант с отличающейся непустой датой, generated-date вариант и обнаружение подмены day_date при прежних counts. Поле включено в оригинальные content hashes, а не исключено вместе с новым execution_reason. API fixture отдельно использует синтетический day_date и проверяет запрет прямой записи и сохранение при status update. Кандидат проверяет точный порядок колонок и PostgreSQL type date, но не объявляет их defaults/triggers или весь Progress path проверенными. Новый успешный владельческий вывод нужен отдельно.
