# Authority source versions and operator readiness

This is a public-source contract, not a hosted catalog snapshot or a report of user authority. Production/Staging mutations, grants/revokes, activation and administrator assignment are outside this review. Payment integration remains deferred in issue #198 after meal-plan generation.

## Read-only inspection

`scripts/security/authority-readiness/read-only.sql` is one SELECT over PostgreSQL metadata. It does not read profile/attestation user rows, invoke application predicates or provisioning functions, write objects, create roles, or change sessions. Execute it with an independently authorized read-only connection. It reports actor/version, profile key/count, existence and privacy of the authority store, known reader/writer source versions, ordinary PostgreSQL extension ownership and managed-platform hints, and the count of eight legacy RPC targets. It does not return function definitions, actual body hashes, ACL dumps or account identifiers.

All expected fingerprints are derived from tracked source bodies. The test recomputes them from the public files and rejects stale fingerprints. An exact body match plus metadata is a version check, not proof that a whole environment is ready. Constraints/indexes/triggers, lineage/provenance, current administrators, retention/account erasure, concurrency, live caller compatibility, recovery and full-schema API/UI acceptance still require review. A missing verified predicate must deny admin; do not manufacture attestations to get a green result.

## Important source dependencies

The complete trusted v2 installer expects `user_profiles.user_id` and adds four protected provenance/time columns and restrictive Premium policies. The 17-column profile candidate #190 instead requires the exact `id_user` schema plus coach/voice settings. These source contracts cannot be treated as interchangeable. An adaptation must be a separate reviewed forward design preserving the production profile/client contract; do not rename keys, install the staging draft verbatim or backfill old flags as authority.

The older `20260921_trusted_entitlement_v2_2_repair.sql` replaces both grant/revoke bodies with statement-clock writers. The later `20260927_adaptive_nutrition_graph_v2_authorities_activation_v1.sql` retains that clock and additionally takes the shared account gate before the capability lineage lock. Replaying the older repair afterward removes the gate call despite still passing its loose ownership/security-metadata preflight. Never select a repair merely because an old note says it was not applied. Map exact current source first and preserve later concurrency bindings. Do not activate the full Graph v2 draft just to obtain these writer bodies.

On ordinary PostgreSQL, relocating pg_trgm requires extension ownership (or appropriate owner-role privileges/superuser); BYPASSRLS is not extension ownership. See PostgreSQL 17 [ALTER EXTENSION](https://www.postgresql.org/docs/17/sql-alterextension.html). Managed Supabase adds platform mechanisms: its [official guidance](https://supabase.com/kb/troubleshooting/cant-change-the-default-privileges-of-supabase_admin-in-the-public-schema) explicitly describes moving relocatable extensions with ALTER EXTENSION from SQL Editor/direct psql even though extension objects can belong to supabase_admin. Therefore **a false ordinary-owner check does not establish a hosted prohibition**. The diagnostic separately reports ordinary ownership and supautils privileged-role/allowlist hints; hints also do not prove the exact platform hook/version/DDL operation works. Do not add an unconditional release blocker based only on the core-owner boolean. Reconcile the exact platform-supported path and test in an appropriately authorized disposable Supabase environment before a separately approved hosted rehearsal/apply. Do not change role memberships, escalate, drop/recreate an extension or use server-file access. The plain PostgreSQL fixture has no Supabase hooks and proves only the ordinary PostgreSQL case.

## Disposable acceptance

Eight cases replay the complete public v2 installer on synthetic base tables and empty auth/attestation stores, then the exact v2.2 repair and only the public shared-gate helper plus two later writer bodies. No full Graph activation, provisioning call, user-data fixture or credential is involved. Tests distinguish absent/readers/private-store metadata, clock-only versus account-gate writer versions, reproduce the old-repair downgrade, reject ALTER EXTENSION for a non-member of another owner role on ordinary PostgreSQL, distinguish platform GUC hints from proof of an executed operation, and run diagnostics inside READ ONLY without changing authority rows or definitions. This is source/metadata acceptance, not payment, full issuer/lineage or live UI acceptance.
