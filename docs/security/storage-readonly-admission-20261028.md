# Storage binary acceptance: read-only admission

Owner `SCOPED_DIARY_PHOTO_OK` in `scoped-diary-photo-Xx1zVk` completes both-user diary CRUD and photo metadata upsert/cleanup on the existing private copy. Original rows, fresh protected contents and checked security were preserved. Actual Storage file service acceptance is still separate; the backup has 63 verified files in three buckets, not a running Storage service.

Review of the [Storage v1.80.2 startup source](https://github.com/supabase/storage/blob/v1.80.2/src/start/server.ts) shows single-tenant normal startup calling `runMigrationsOnTenant`, with the optional migration freeze passed into the runner. A freeze setting is not evidence that startup makes no schema changes. Do not launch the default server against the preserved candidate until its actual binary and schema have been reviewed. No blanket permission repair, disabling RLS or substituting a newer image is authorized by a failed check.

The [file backend](https://github.com/supabase/storage/blob/v1.80.2/src/storage/backend/file.ts) reads versioned backend paths and filesystem attributes. The [adapter](https://github.com/supabase/storage/blob/v1.80.2/src/storage/backend/adapter.ts) chooses a version separator by configuration. Downloaded `storage-files/<bucket>/<bucket>/<name>` paths are not automatically a valid backend layout. A bucket/name must be bound to the actual database object version; do not infer a layout from file counts alone. The [self-hosting documentation](https://supabase.com/docs/guides/self-hosting/docker#using-file-backend-in-storage-on-macos) recommends a named Docker volume for the macOS file backend because of bind-mount attribute/permission limitations. A future service must get its own staged volume, never a writable mount of the backup. The release tag and the package.json version need not have the same value.

`storage-preflight.mjs --inspect-local-storage BACKUP_DIR SCOPED_WRITE_EVIDENCE_DIR` is a standalone small tool using Node built-ins. It requires the successful diary/photo receipt, exact existing database ID/image/volume/network-none, the same running Auth/API containers, and the already cached linux/arm64 `public.ecr.aws/supabase/storage-api:v1.80.2` image. It does not pull/build an image, start Storage, mount files/volumes into a container, inject service Env or inspect secrets.

It saves private read-only Storage object/bucket/migration/catalog observations, verifies the exact 63 local files and manifest hashes against actual object names/sizes/opaque versions, then inspects only an allowlist of public package/compiled-source files inside an ephemeral read-only non-root network-none image container. It never imports the application or executes its normal entrypoint. A separate local `supabase_storage_admin` connection runs only a read-only identity query using the existing container password internally; it prints no password. Failure to connect is a diagnostic flag, not permission to reset a role. Independent read-only Storage observations after these probes must match the first observation exactly.

Evidence stays in a new owner-only `storage-preflight-*` folder. Public output contains only the observation marker, immutable image ID, connection boolean, count of known compiled paths found and public package version. No object names, owners, stored contents, tokens or private logs need to be sent to chat. `STORAGE_PREFLIGHT_CAPTURED` means observation captured, not service ready, HTTP binary verified, release ready or deployment approved.

Tests cover exact name/size/hash/version binding across 63 files, same-size tampering, extra files, symlinks, malformed scopes/versions, read-only image inspection without importing even deliberately crashing application source, unsupported CLI targets, and native PostgreSQL execution of the exact observation SQL. Only the disposable CI database gets fixture CREATE/INSERT statements; the owner command never executes those fixtures.

The next service implementation must use the captured image/migration state, resolve backend mapping explicitly, stage a separately verified copy into a named volume, prevent unreviewed startup migrations and background jobs, bind only shared private loopback without published ports, and verify original binary hashes plus narrowly scoped A/B upload/download/foreign-access/cleanup behavior. Existing source SQL dumps, encrypted archive and the original 63 files remain unchanged. Program/mealService/UI and hosted-release gates remain separate.
