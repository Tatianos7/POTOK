# Единая среда сборки — 27 октября 2026

Предыдущая ревизия #219 закрепила разницу Node18 в Pages, Node20 в root PR checks и Node22 в combined browser CI. Новый кандидат вводит один файл `.node-version` со значением `24.22.1`; все три workflow читают его через `node-version-file`. Это та же точная версия, которая уже закреплена в изолированном браузерном runtime #218. Изменение файла версии включено в path-filter combined CI, чтобы оно не обходило API/UI-проверку.

Версия выбрана как уже проверенный в этом пакете инструмент, а не утверждение о последней доступной версии Node. Остальные самостоятельные SQL/fixture workflow сохраняют свои версии: они не собирают Pages или настоящий браузерный клиент. Package.json, package-lock.json, зависимости, приложение, SQL-кандидаты и manifest изолированного браузера не меняются. Снимок release-scope-20261027 остаётся историческим отчётом о точном #218 и не переписывается под новый кандидат.

## Проверки кандидата

В текущем рабочем окружении Node v24.22.1 успешно выполнены:

- `npm ci` по существующему lockfile: 466 пакетов, lockfile неизменён.
- `npm run build` с пустыми VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY: TypeScript, Vite и postbuild, включая dist/404.html, завершились успешно. Это проверка сборки, не запуск приложения с настоящим backend.
- 161 тест: 31 дневник/аккаунт; 19 snapshot/Premium/quarantine; 77 read-only/persistence/error/evidence; 34 Nutrition Integrity. Для TypeScript использован `node --import tsx --test`: локальный CLI tsx не может создавать IPC socket (EPERM), loader исполняет те же тестовые файлы без этого IPC. В GitHub сохраняются исходные npm/tsx-команды, поэтому результат workflow сверяется отдельно.
- `node scripts/security/release-scope.mjs --verify` и `git diff --check`.

При первом локальном запуске отсутствовали public/data/acceptance файлы из-за частичного checkout. Они получены из той же Git-ревизии; итоговая полная сборка и тесты выше прошли без изменения исходников или ослабления проверок. Существующие предупреждения об устаревших browser-data, крупных bundle и смешанном импорте mealService не превращены в успех без оговорок: сборка возвращает 0, эти предупреждения этим кандидатом не устраняются.

## Условия приёма и границы

До принятия сверить root PR checks и combined API/browser на точном head этого кандидата. Первый доказывает команды обычного workflow, второй — реальный синтетический Auth/API/UI и изолированный браузер при новом host Node. Успех этих CI не доказывает arm64 Mac или поздние результаты владельца; выполненная владельцем работа сохраняет статус «сообщена, доказательства ожидают сверки».

Deploy workflow не выполняется для этого PR; triggers, Pages permissions, secrets и команды публикации не расширены. Принятие в master по-прежнему автоматически публикует Pages и требует отдельного согласованного выпуска. Пустые CI env проверяют сборку без секретов, но не фактическую конфигурацию hosted-сборки/доступность Supabase. Сам production build с настоящими настройками здесь не выполнялся.

Это исправляет расхождение конфигураций сборки; не создаёт hosted forward/recovery batch, не решает двустороннюю несовместимость execution_reason/plan_payload и не активирует генератор/Edge. Следующая отдельная работа — конкретный совместимый переход program actions с проверяемыми preconditions/recovery; старые широкие права не возвращать. Порядок владельца неизменён: завершение согласованного security-этапа → фейерверк → генерация питания → проверка квитанций #198.
