# Combined committed local application acceptance

The restored-copy rehearsal in PR191 rolled all four candidates back together and checked actual row contents and metadata. This separate CI job creates a new unlinked local Supabase with synthetic profile/catalog fixtures and eight harmless SECURITY DEFINER RPC stand-ins. It commits all four pinned, SHA-256 verified candidate bodies in one transaction, repeats their effective permission checks after relocation, and verifies the committed state on a new database connection before starting browser requests.

The actual Login/Profile components, AuthProvider and profileService then run against real local Auth, Mailpit and PostgREST. Checks cover OTP login, default profile creation, direct protected-column UPDATE denial through the API, a catalog ILIKE query after pg_trgm relocation, ordinary profile save, actual avatar file selection and reload, session refresh, offline pending queue recovery and A-to-B ownership isolation. Browser traffic is limited to the local API and Vite origins. CLI logs, actual codes, keys and sessions are kept only in the ephemeral runner. The browser step is bounded to three minutes; only the local disposable project is stopped and its volumes removed afterwards.

The setup and browser scripts require GITHUB_ACTIONS=true and the exact disposable project directory. Setup refuses existing Auth users or a profile table and uses a fixed local Docker container/socket. It cannot apply changes to the owner's restored backup or to a hosted project through a URL/flag. The original PR191 manual runner remains rollback-only. The static email placeholder template alone is readable by Kong; actual secrets remain private.

RPC stand-ins exercise grant coexistence, not business authorization, provider receipts or trusted billing/admin authority. The synthetic catalog query does not reproduce all production food search routines. The small fixture is not the owner's restored 112-table dataset. This job therefore complements, rather than replaces, persistent application/API checks against a restored full schema on an owner-controlled computer. Mobile/PIN/full-router flows, hosted provider/template configuration, unknown callers and a hosted deployment decision remain separate. Production and Staging are unchanged; no runtime application files or hosted migrations are added.
