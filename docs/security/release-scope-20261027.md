Для hosted выпуска нужен отдельно рассмотренный forward batch; автоматическая замена ROLLBACK на COMMIT его не создаёт.

## Подтверждённая несовместимость последовательного перехода

Новый programDeliveryService отправляет execution_reason даже при старте/завершении дня. На старой схеме поле отсутствует — такой запрос не сможет сохраниться. После quarantine старый клиент всё ещё пытается записать plan_payload при пропуске/адаптации; новые права это блокируют. Поэтому безопасного предположения «сначала весь клиент» или «сначала вся база, пользователи продолжат как раньше» нет.

Нужен один из отдельно рассмотренных вариантов: согласованное окно недоступности действий с программами и установка совместимой версии после подтверждённого SQL, либо отдельный совместимый промежуточный клиент/схема. Такой bridge в текущем составе не найден. При выбранном окне перед возвратом действий проверяются status/reason и блокировка старых plan writes, обновление старой вкладки/сборки, отсутствие подмены plan content и история. Простой откат на старый клиент не является восстановлением совместимости.

## Публикация и окружение сборки

Неизменённый deploy.yml запускает Pages при push в main/master и двух feature-ветках. Следовательно, merge в master имеет эффект публикации, а не только сохранения ревью. Сейчас публикация не выполнялась.

Deployment выбирает Node18, root CI — Node20, combined browser — Node22, отдельный браузерный контейнер — Node24.22.1. Успешные проверки этих сред не доказывают прохождение именно deployment Node18. Это обнаруженный разрыв покрытия, не утверждение о воспроизведённом падении. Перед выпуском нужно выбрать согласованное окружение сборки и проверить его без публикации/секретов, затем включить это решение в точный release diff.

1. Зафиксировать единый выбранный commit и client/SQL dependency matrix из этой ревизии. Согласовать реальное временное отключение legacy generation и способ перехода program writes.

3. Выбрать и проверить точную среду сборки; сверить release diff со свежей master, исключить случайное включение других Graph/Nutrition drafts.
4. Восстановить поздние результаты из несинхронизированного чата при их доступности; по ним закрывать соответствующие gates. Сохранять отдельными факты о полных данных, реальном API/UI и Storage binaries.
5. Перед hosted-окном сверить drift и свежий приватный backup/recovery. Подготовить безопасный forward repair; восстановление старых широких прав/небезопасных функций не является обычным rollback. Проверить реальные обычные/чужие пути после применения.
