# Joint restored-copy rehearsal

The four earlier candidates were tested individually. `scripts/security/joint-rehearsal/run.mjs` composes their pinned, SHA-256 verified bytes into one BEGIN/ROLLBACK transaction: TRUNCATE containment, profile column allowlist, anonymous RPC EXECUTE containment, then pg_trgm relocation. Their outer transaction statements are removed only after exact input checks; all individual preconditions remain. Permission postconditions are repeated after the final candidate so coexistence is checked. There is no COMMIT in the generated script.

The manual runner accepts only the POTOK_BACKUP_2026-10-24 directory, an exact three-file SHA256SUMS manifest, and a data.sql with 112 COPY blocks / 14,888 rows (auth 26, public 81, storage 5). It targets only the fixed healthy Docker container supabase_db_POTOK_BACKUP_2026-10-24 with a Supabase PostgreSQL 17 image. It captures the container ID and uses an explicitly local /run/postgresql socket as non-superuser postgres, with normal trigger state and ON_ERROR_STOP. It has no hosted project parameters, CLI link/login operations or connection URLs. No Docker images or new services are started. Network requests only retrieve four immutable public repository inputs; changed bytes abort.

A private temporary baseline records public/extension ACLs and identities, public policies/constraints/triggers, defaults, extension membership and public index state. For every COPY table it verifies dump row counts and computes a SHA-256 fingerprint from sorted SHA-256 row JSON fingerprints, including duplicates. It compares actual table contents inside the combined transaction and again after rollback. No row values, routine definitions or private ACL snapshots are printed or written to the host. After rollback the metadata baseline must match exactly; after disconnect the temporary evidence disappears. Before/after checksum verification also protects the three source SQL dump files. Generated SQL and the four public inputs are retained in a fresh private joint-rehearsal-* subdirectory of the local backup, without overwriting the backup or archive.

Expected terminal markers: JOINT_CHECKS_OK, JOINT_ROLLBACK_OK, then JOINT_REHEARSAL_OK. Any earlier SQL failure stops psql and disconnects, rolling back its open transaction. Such a failure does not establish successful post-rollback verification; investigate the reported error before repeating. A successful run returns to the restored copy's previous baseline, including any earlier local TRUNCATE containment. It does not apply the new restrictions permanently. Internal supabase_admin default grants can remain as explicitly reported by the existing TRUNCATE candidate.

Tests use synthetic fixtures, non-superuser postgres and PostgreSQL 17. They cover coexistence, exact rollback, an already-contained TRUNCATE baseline, failure after the first candidate, failure at the last candidate, same-count content changes, malformed COPY data and changed/extra transaction inputs. Native CI additionally streams the complete generated SQL through actual psql stdin. Fixture installation briefly elevates only to install pg_trgm with appropriate owned member objects, then demotes before every rehearsal; it does not reproduce hosted managed-role hooks. Neither fixture tests nor a successful restored-copy run prove application/API behavior for all four persistent changes together, hosted grant authority, billing/RPC authorization repair or complete disaster recovery. Existing individual application acceptance remains separate.

The public repository contains only generic runner/test/runbook code. The owner's backup, generated table manifest, row hashes and metadata evidence are not uploaded. Production and Staging remain unchanged. This is not a hosted migration or hosted apply approval.

Reference: [PostgreSQL 17 binary SHA-256 and encoding functions](https://www.postgresql.org/docs/17/functions-binarystring.html).
