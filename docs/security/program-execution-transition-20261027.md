# Переход действий с программами — кандидат 27 октября 2026

Основа — #220, Node24.22.1. Выбран клиентский переход с явной временной недоступностью day actions до готовности схемы, без промежуточного расширения прав или нового SQL/RPC. SQL-источники двенадцати кандидатов не меняются, готовый hosted forward batch этим изменением не создаётся.

## Реализованное поведение

Новый ProgramExecutionService используется startDay, completeDay и skipDay. Перед каждой записью он подтверждает пользователя и выполняет GET program_sessions с select=execution_reason и limit=0. Это реальный запрос к REST projection без чтения строк и без пробной мутации. Старая схема, отсутствующая колонка/права, stale cache, ошибка сети или некорректный ответ дают PROGRAM_EXECUTION_UNAVAILABLE с сообщением «Действия с программой временно недоступны: база обновляется. Попробуйте позже». Успех probe не доказывает установленный security batch; сами права/RLS отдельно проверяются на сервере и в release preflight.

На готовой схеме выбирается ровно одна видимая session по program/date и, для complete/skip, типу программы. Нет строки, две строки, неправильный ID или session_type — отказ до PATCH. Перед PATCH повторно сверяется аккаунт. Запись ограничена уникальным id и тем же program/date/type; отправляются только status/execution_reason и требуется возвращённый id ровно одной строки. Ноль обновлённых строк, неподтверждённый ответ или ошибка не становятся успехом и не запускают последующие действия delivery service. Нет автоматического повтора мутаций или fallback на plan_payload.

GET и PATCH cache могут обновляться неодновременно: поздний PGRST204/42703/42501 на PATCH также даёт временную недоступность, без повторной записи. Неизвестная сетевая ошибка PATCH остаётся ошибкой с неподтверждённым исходом: сначала обновить/сверить серверное состояние, не повторять вслепую. Readiness не кешируется и не служит разрешением от имени другого аккаунта; RLS остаётся окончательной границей.

Не меняются pause/resume, feedback, вторичные trust/program-status annotations после успешно сохранённого дня, экраны/маршруты и фактологический дневник. Этот кандидат не вводит новый UI действий Today и не доказывает UI-приёмку этих действий. Старые generation/replan/adapt остаются явно выключены, старый plan payload не заменяется.

## Порядок внедрения для отдельного согласования

| Состояние | Что ожидается |
| --- | --- |
| Старый backend + новый клиент | Start/complete/skip дают понятную временную недоступность; ни одного PATCH к session. Чтение планов продолжает зависеть от существующей серверной совместимости |
| Quarantine установлен, GET/PATCH cache ещё не готов | Отказ без legacy fallback/повторов; действия открываются при следующей попытке только после готовности обоих путей |
| Новый backend + новый клиент | Own start/complete/skip с подтверждённым id; чужая/неоднозначная session не меняется; plan_payload/day_date сохранены |
| Новый backend + старая открытая вкладка/сборка | Старые content/version/adaptation writes должны быть запрещены. Совместимость старого клиента не обещается; вкладку/клиент нужно обновить в согласованном окне |

Практический порядок: определить точный клиентский commit/hosted batch и окно; подготовить актуальную копию/recovery и read-only drift proof; поставить новый клиент и обновить все используемые вкладки/сборки; убедиться в явной временной недоступности day actions; только после отдельного одобрения выполнить reviewed hosted batch; проверить committed права, REST cache, own/foreign actions и неизменность плана/истории. Установка нового клиента до схемы теперь не отправляет несовместимую запись execution_reason, но это намеренное окно недоступности, а не непрерывная работа старых клиентов.

При сбое схемы новый клиент остаётся закрытым; при сбое клиента после quarantine нельзя возвращать старые широкие права или считать старую сборку безопасным rollback. Нужен исправленный совместимый клиент/forward repair. Старые installer/owner A/B/browser команды не повторять: более поздняя работа владельца сообщена выполненной, доказательства из несинхронизированной истории требуют сверки при доступности.

## Проверки и область доказательств

16 локальных тестов выполняют настоящий TypeScript client logic с управляемыми ответами: schema/cache/permission/network errors, logout/account switch, чужая/отсутствующая/неоднозначная session, неверный тип/receipt, zero-row PATCH, отсутствие повторов и fallback, bounded payload и остановка downstream. TypeScript/build проверяются также обычным root CI.

В combined API CI добавлена отдельная проверка через настоящий locked supabase-js, OTP-issued user JWT, Auth и PostgREST. Она вызывает тот же ProgramExecutionService до quarantine (все три действия закрыты без PATCH, полные session bytes сохранены), затем после quarantine (три own действия, own B, чужой доступ и смена аккаунта; plan_payload/day_date неизменны; старый plan_payload PATCH запрещён). Это тест сервиса/API, не эмуляция клика UI. Старые проверки SQL, планов, истории и diary snapshots не удалены и не ослаблены.

Изолированный browser source manifest обновлён только для изменённого programDeliveryService и нового programExecutionService; теперь 602 публичных входа. Обновлён его закреплённый SHA. Это требует нового exact-head CI runtime, а не повторной установки владельческой базы. Mac/Production/Staging не используются. Результаты GitHub сохраняются в описании Draft PR после завершения, отдельно от локальных тестов.
