## Scope

Architecture/spec-only design for future Supabase data model behind POTOK Premium:

- 14-day Premium plans;
- plan days;
- meal slots;
- ready POTOK recipes;
- recipe ingredients, hints, and steps;
- meal replacement options;
- shopping list aggregation strategy;
- selected Premium plan linkage to a user's goal.

No runtime code changes, DB migration execution, Supabase deploy, payment/auth changes, diary/workout writes, recipe import, AI runtime, voice input, commit, push, or PR work was done.

This report is a design artifact only.

## Current UI Basis

Current deployed UI mocks provide the behavioral shape for the future model:

- Home premium/demo state shows `Мой Поток` and `Сборник рецептов`.
- `/today` contains the Premium plan flow: plan list -> 14-day plan detail -> day detail -> meal detail -> replace meal, plus shopping list.
- `/premium-recipes` contains the Premium recipe library and recipe detail mock.
- Current Today mock data is local in `src/pages/Today.tsx`:
  - plan metadata;
  - 14 generated days;
  - day macros;
  - meal slots;
  - meal detail ingredients/hints/steps;
  - replacement options;
  - derived shopping groups.
- Current Premium recipe mock data is local in `src/pages/PremiumRecipes.tsx`.

Existing persisted app surfaces that should stay separate:

- `public.recipes` is user-owned and uses `user_id`.
- `public.recipe_ingredients` belongs to user recipes through `recipes.user_id`.
- `favorite_recipes` and `recipe_collections` are user-specific relations for the free/user recipe area.
- `recipeDiaryService` writes recipe snapshots into diary only after user action through `mealService.addMealEntry`.
- `diaryCreateService` creates diary entries from explicit, resolved payloads and stores nutrition snapshots.
- `user_goals` stores goal macros and goal metadata used by Goal/Today.

## Core Principles

- **Premium recipes are not user recipes.** Do not mix POTOK ready recipes with `public.recipes`, `/nutrition/recipes`, favorites, or user collections.
- **Plan is not diary fact.** A Premium plan is a recommendation/schedule, not an eaten meal.
- **Diary writes are explicit only.** Future `Добавить в дневник` must create diary entry snapshots only after user confirmation.
- **No historical recompute.** Changing a Premium recipe or plan later must not mutate old diary entries or past selected-plan days.
- **No AI-generated records yet.** Until AI runtime exists, rows should be curated/admin-created or seeded, not marked as generated by AI.
- **No payment enforcement in this spec.** Entitlement enforcement can be layered in service/RLS later, but this report does not design payment flows.

## Proposed Tables

### `premium_plans`

Catalog table for ready POTOK plans.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `title text not null`
- `subtitle text`
- `goal_type text`
- `duration_days integer not null default 14`
- `difficulty text`
- `is_active boolean not null default true`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Recommended MVP constraints:

- `duration_days > 0`
- `goal_type` nullable at first, because current goal labels may be localized/free-form.
- `difficulty` nullable at first, because current UI uses copy such as simple start/home/quick rather than strict enum.

Recommended indexes:

- `(is_active, goal_type)`
- `(created_at desc)`

### `premium_plan_days`

Catalog table for each day inside a Premium plan.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_plan_id uuid not null references public.premium_plans(id) on delete cascade`
- `day_number integer not null`
- `calories integer`
- `protein numeric(8,2)`
- `fat numeric(8,2)`
- `carbs numeric(8,2)`
- `workout_title text`
- `workout_duration_min integer`
- `workout_focus text`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Recommended constraints:

- `unique (premium_plan_id, day_number)`
- `day_number > 0`
- nutrition fields nullable in MVP so workout-only or incomplete draft days can exist before publishing.

Recommended indexes:

- `(premium_plan_id, day_number)`

### `premium_meal_slots`

Catalog table for planned meal slots inside a plan day.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_plan_day_id uuid not null references public.premium_plan_days(id) on delete cascade`
- `meal_type text`
- `title text not null`
- `calories integer`
- `protein numeric(8,2)`
- `fat numeric(8,2)`
- `carbs numeric(8,2)`
- `sort_order integer not null default 0`

Recommended constraints:

- `meal_type in ('breakfast','lunch','dinner','snack')` once localization mapping is stable.
- `unique (premium_plan_day_id, sort_order)`.

Nullable MVP fields:

- `meal_type`, because current UI title is localized (`Завтрак`, `Обед`, `Ужин`, `Перекус`).
- macro fields, because a meal slot could be recipe-backed and derive macros later.

Recommended indexes:

- `(premium_plan_day_id, sort_order)`
- `(meal_type)`

### `premium_recipes`

Separate POTOK ready recipe catalog. This must not reuse `public.recipes`.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `title text not null`
- `category text`
- `calories integer`
- `protein numeric(8,2)`
- `fat numeric(8,2)`
- `carbs numeric(8,2)`
- `cooking_time_min integer`
- `difficulty_label text`
- `is_active boolean not null default true`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Recommended MVP nullable fields:

- `category`, until final taxonomy is approved.
- macro fields, if early content is being drafted.
- `cooking_time_min`, because not every recipe will have precise time at import.
- `difficulty_label`, because current UI uses human-readable labels.

Recommended indexes:

- `(is_active, category)`
- `(title)`
- `(created_at desc)`

### `premium_recipe_ingredients`

Ingredient rows for Premium recipes. These should support shopping aggregation and future diary snapshots.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_recipe_id uuid not null references public.premium_recipes(id) on delete cascade`
- `ingredient_name text not null`
- `amount_g numeric(10,2)`
- `display_amount text`
- `sort_order integer not null default 0`

Optional later columns:

- `canonical_food_id uuid references public.foods(id) on delete set null`
- `shopping_group text`
- `shopping_name text`
- `shopping_unit text`
- `shopping_amount numeric(10,2)`

MVP recommendation:

- Keep `amount_g` nullable because items like `Банан — 1 шт` may be more useful as display units.
- Keep `display_amount` nullable but strongly recommended for user-facing copy.
- Do not require `canonical_food_id` in MVP; resolving to food catalog can be a later content QA phase.

Recommended indexes:

- `(premium_recipe_id, sort_order)`
- `(ingredient_name)`

### `premium_recipe_steps`

Preparation steps for Premium recipe detail.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_recipe_id uuid not null references public.premium_recipes(id) on delete cascade`
- `step_number integer not null`
- `instruction text not null`

Recommended constraints:

- `unique (premium_recipe_id, step_number)`
- `step_number > 0`

Recommended indexes:

- `(premium_recipe_id, step_number)`

### `premium_recipe_hints`

Portion hints without scales.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_recipe_id uuid not null references public.premium_recipes(id) on delete cascade`
- `hint_text text not null`
- `sort_order integer not null default 0`

Recommended indexes:

- `(premium_recipe_id, sort_order)`

### `premium_meal_recipe_options`

Join table between a meal slot and valid recipe choices/replacements.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `premium_meal_slot_id uuid not null references public.premium_meal_slots(id) on delete cascade`
- `premium_recipe_id uuid not null references public.premium_recipes(id) on delete restrict`
- `option_type text`
- `label text`
- `sort_order integer not null default 0`

Recommended constraints:

- `unique (premium_meal_slot_id, premium_recipe_id)`
- `option_type` can later be constrained to values such as `primary`, `simpler`, `lower_calorie`, `higher_protein`, `no_cook`, `similar_macros`.

MVP recommendation:

- Keep `option_type` and `label` nullable/free-form until replacement filter taxonomy is stable.

Recommended indexes:

- `(premium_meal_slot_id, sort_order)`
- `(premium_recipe_id)`
- `(option_type)`

### `user_premium_plan_selections`

User-specific selected plan state. This table is recommended even though it was not in the initial table list, because it safely connects a Premium plan to a user's goal without mutating the catalog.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `user_id uuid not null references auth.users(id) on delete cascade`
- `user_goal_id uuid references public.user_goals(user_id) on delete set null`
- `premium_plan_id uuid not null references public.premium_plans(id) on delete restrict`
- `status text not null default 'active'`
- `start_date date`
- `selected_at timestamptz not null default now()`
- `completed_at timestamptz`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Recommended constraints:

- `status in ('active','paused','completed','archived')`.
- Optional partial unique index for one active Premium plan per user:
  - `unique (user_id) where status = 'active'`.

MVP nullable fields:

- `user_goal_id`, because a user may preview/select from demo or no-goal state later.
- `start_date`, because plan preview and plan activation can remain separate steps.

Recommended indexes:

- `(user_id, status, selected_at desc)`
- `(premium_plan_id)`
- `(user_goal_id)`

### `user_premium_meal_selections`

User-specific local/persisted replacement state. This should store what the user chose without rewriting the catalog or historical diary.

Recommended columns:

- `id uuid primary key default gen_random_uuid()`
- `user_premium_plan_selection_id uuid not null references public.user_premium_plan_selections(id) on delete cascade`
- `premium_meal_slot_id uuid not null references public.premium_meal_slots(id) on delete restrict`
- `selected_premium_recipe_id uuid references public.premium_recipes(id) on delete restrict`
- `selected_at timestamptz not null default now()`
- `created_at timestamptz not null default now()`
- `updated_at timestamptz not null default now()`

Recommended constraints:

- `unique (user_premium_plan_selection_id, premium_meal_slot_id)`.

MVP nullable fields:

- `selected_premium_recipe_id`, if a user can explicitly clear a replacement back to default.

Recommended indexes:

- `(user_premium_plan_selection_id)`
- `(premium_meal_slot_id)`
- `(selected_premium_recipe_id)`

### `premium_shopping_items` vs Derived Shopping List

Do not add `premium_shopping_items` as a user table in MVP.

Recommended MVP strategy:

- Derive shopping list from selected plan days and selected recipes:
  - `premium_plan_days`;
  - `premium_meal_slots`;
  - `premium_meal_recipe_options`;
  - `user_premium_meal_selections`;
  - `premium_recipe_ingredients`.
- Aggregate by normalized display product key over selected period.
- Keep checkbox state local at first, or add a small user-only table later.

Optional later table for persistent checked state:

- `user_premium_shopping_checks`
  - `id uuid primary key default gen_random_uuid()`
  - `user_id uuid not null references auth.users(id) on delete cascade`
  - `user_premium_plan_selection_id uuid not null references public.user_premium_plan_selections(id) on delete cascade`
  - `period_days integer not null`
  - `shopping_key text not null`
  - `is_bought boolean not null default false`
  - `updated_at timestamptz not null default now()`
  - `unique (user_premium_plan_selection_id, period_days, shopping_key)`

Do not store generated product rows for every day unless the product team explicitly needs share/export/history. Derived lists avoid stale data and reduce migration surface.

## Relationships

Recommended source-of-truth graph:

- `premium_plans` owns `premium_plan_days`.
- `premium_plan_days` owns `premium_meal_slots`.
- `premium_recipes` owns ingredients, steps, and hints.
- `premium_meal_recipe_options` connects a meal slot to one or more valid Premium recipes:
  - one option can be the default recipe;
  - other options can support filters such as easier, lower calorie, more protein, no-cook, similar macros.
- `user_premium_plan_selections` connects a user and optional `user_goals` row to the catalog plan.
- `user_premium_meal_selections` overrides individual meal slots for a user's selected plan.

Recommended selected meal resolution:

1. Load active `user_premium_plan_selections`.
2. Load plan days and meal slots.
3. For each meal slot, check `user_premium_meal_selections`.
4. If a selected recipe exists, use it.
5. Otherwise, use the primary/default `premium_meal_recipe_options` row.

## RLS Principles

Catalog tables:

- `premium_plans`
- `premium_plan_days`
- `premium_meal_slots`
- `premium_recipes`
- `premium_recipe_ingredients`
- `premium_recipe_steps`
- `premium_recipe_hints`
- `premium_meal_recipe_options`

Recommended RLS:

- Enable RLS on all tables.
- Authenticated users can `select` active catalog rows.
- Mutations should be denied to regular authenticated users.
- Admin/service role can insert/update/delete through controlled back-office scripts or service endpoints.
- If entitlement enforcement is later needed at DB level, add a subscription/entitlement predicate in select policies in a separate payment/auth phase.

User tables:

- `user_premium_plan_selections`
- `user_premium_meal_selections`
- optional `user_premium_shopping_checks`

Recommended RLS:

- Users can select/insert/update/delete only their own rows.
- `user_premium_meal_selections` ownership should be checked through parent `user_premium_plan_selections.user_id`.
- No user policy should allow mutating catalog recipes/plans.

## Snapshot / Write-Path Rules

Future `Добавить в дневник` must not copy a plan row directly into diary as a live reference.

Recommended write path:

1. User opens meal detail.
2. User taps `Добавить в дневник`.
3. UI shows explicit confirmation with date, meal type, recipe title, grams/serving, calories/macros.
4. Service resolves the selected Premium recipe into diary insert payload.
5. Diary receives snapshot fields:
   - `product_name`;
   - `weight`;
   - `calories`;
   - `protein`;
   - `fat`;
   - `carbs`;
   - optional `fiber`;
   - `meal_type`;
   - date;
   - idempotency key.
6. Historical diary entries do not reference live Premium recipe nutrition for recalculation.

Recommended optional future diary metadata:

- `source_type = 'premium_recipe'`
- `source_id = premium_recipes.id`
- `source_snapshot jsonb`

These should be additive and nullable. Do not require them for existing diary rows.

Important:

- Do not use `planned = true` diary entries as the Premium plan source of truth.
- Do not pre-write all 14 days to `food_diary_entries`.
- Do not mutate old diary entries when a Premium recipe is edited.

## Shopping List Strategy

Recommended MVP:

- Build shopping lists as a derived read model from selected days and selected recipes.
- Aggregate ingredients for selected period: 1, 2, 3, or 7 days.
- Group by `shopping_group` if present; otherwise use fallback groups from curated ingredient metadata or UI heuristics.
- Aggregate by normalized `shopping_name` and compatible unit.
- Preserve user-facing `display_amount` for recipe detail, but use numeric fields for aggregation where possible.

Aggregation rules:

- Same product + same unit -> sum quantities.
- Same product with grams and pieces should not be blindly summed; use curated `shopping_unit` and `shopping_amount` later.
- If amount is display-only, show separate line or require content QA before publishing.
- Meal replacements should affect future shopping list aggregation for the selected user plan.

Persistent checked state:

- Keep bought checkboxes local/mock until product requires persistence.
- If persistence is needed, add `user_premium_shopping_checks` later.
- Do not store generated shopping list rows as source of truth in MVP.

## Meal Replacement Strategy

Catalog:

- Replacement candidates live in `premium_meal_recipe_options`.
- Filters are metadata (`option_type`, `label`) rather than AI calls.

User state:

- A replacement writes only to `user_premium_meal_selections`.
- It changes the user's selected plan view and future shopping aggregation.
- It does not rewrite `premium_meal_slots`.
- It does not rewrite `premium_recipes`.
- It does not change historical diary entries.

Day macro recalculation:

- MVP can show day-level planned macros from `premium_plan_days`.
- Later, after replacement persistence, the UI can calculate adjusted day totals from selected recipes.
- Store adjusted totals only if there is a clear product reason; otherwise derive them to avoid stale data.

## Risks / Do-Not-Do List

- Do not store POTOK Premium recipes in user-owned `public.recipes`.
- Do not route Premium library through `/nutrition/recipes`.
- Do not let users edit POTOK catalog rows.
- Do not create diary entries automatically when a plan is selected.
- Do not prefill 14 days into `food_diary_entries`.
- Do not rely on `planned` diary rows as the plan model.
- Do not recompute historical diary entries after recipe/plan edits.
- Do not make `goal_type`, `category`, `difficulty_label`, `meal_type`, or `canonical_food_id` too strict before taxonomy/content QA is complete.
- Do not add AI-generated flags/records until AI runtime and review rules exist.
- Do not combine payment/subscription enforcement with initial data model migrations.
- Do not add shopping list backend persistence until local/mock checkbox behavior has a clear product requirement.
