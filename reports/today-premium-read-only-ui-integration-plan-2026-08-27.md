## Proposed Service Layer

Create a read-only service layer, for example `src/services/premiumCatalogService.ts`.

Responsibilities:

- use the existing `supabase` client from `src/lib/supabaseClient.ts`;
- expose read-only functions:
  - `getActivePremiumPlans()`;
  - `getPremiumPlanDetail(planId)`;
  - `getPremiumPlanDay(planId, dayNumber)`;
  - `getPremiumPlanDays(planId)`;
  - `getPremiumMealSlots(dayId)`;
  - `getPremiumRecipeLibrary()`;
  - `getPremiumRecipeDetail(recipeId)`;
  - `getMealRecipeOptions(slotId)`;
  - `buildDerivedShoppingList(planId, dayRange)`;
- never call `insert`, `update`, `upsert`, `delete`, or RPC mutation paths;
- return typed DTOs shaped for current UI;
- catch Supabase unavailable/read failures and return a typed fallback result;
- keep old mock data as fallback until staging reads are stable.

Suggested guardrails:

- add tests that inspect `premiumCatalogService` source and assert no mutation methods are used;
- keep all first-pass functions catalog-only;
- avoid auth/payment enforcement changes;
- do not introduce service-role keys or non-anon keys in frontend code.

## Fallback Strategy

Use a demo/read mode resolver:

- first try read-only staging catalog if:
  - Supabase client is configured;
  - feature flag/read mode is enabled;
  - user has Premium or demo Premium access.
- if query fails or seeded data is incomplete:
  - fall back to existing page mock arrays;
  - preserve current UX copy and disabled write buttons;
  - avoid noisy user-facing technical errors in the first integration.

Possible flag:

- `VITE_PREMIUM_CATALOG_READ_MODE=staging_readonly`

Default:

- keep current mock behavior unless the flag is explicitly enabled.

## Route-By-Route Plan

`/premium-recipes` library:

- Phase 2 target.
- Replace local `premiumRecipes` read source with `premiumCatalogService.getPremiumRecipeLibrary()`.
- Map `category` to existing category chips.
- Display calories/macros/cooking time from `premium_recipes`.
- Keep disabled actions.
- Fallback to current mock recipe array.

`/premium-recipes` detail:

- Phase 2 target.
- Read recipe base row plus ingredients, steps, and hints.
- Keep URL/local selected recipe state.
- Keep `Добавить в план` and `Добавить в дневник` disabled.
- No writes to `public.recipes`, diary, or user selection tables.

`/today` plan list:

- Phase 3 target.
- Read active plans from `premium_plans`.
- Show the seeded active 14-day plan.
- Continue to support existing goal/no-goal empty state.
- Do not create `user_premium_plan_selections` from `Выбрать план`.
- Button can remain disabled, no-op, or clearly mocked in implementation.

Plan detail:

- Phase 3 target.
- Read selected plan and seeded day rows.
- Show only days returned by staging for the first pass: day 1 and day 2.
- Do not fake full 14-day completeness from DB data; if UI needs 14-day structure, show unavailable days as locked/placeholder only in a separate approved UX decision.

Day detail:

- Phase 3 target.
- Read `premium_plan_days` and `premium_meal_slots`.
- Map seeded breakfast/lunch/dinner/snack rows.
- Use meal slot macros for row summaries.
- Keep day state controls local-only.
- Keep `Подтвердить день` disabled/no-write.

Meal detail:

- Phase 3 target.
- Resolve the primary option through `premium_meal_recipe_options`.
- Read selected `premium_recipes`, ingredients, steps, and hints.
- Keep `Добавить в дневник` disabled.
- Do not write `food_diary_entries`.

Replacement view:

- Phase 4 target.
- Read replacement candidates through `premium_meal_recipe_options`.
- Show `primary` and `replacement` option types.
- Selecting a replacement may remain local UI state only.
- Do not create/update `user_premium_meal_selections`.

Shopping list:

- Phase 5 target.
- Keep derived/mock/read-only.
- Option A: keep current `shoppingGroups` mock until richer seed exists.
- Option B: derive grouped ingredients from Premium recipe ingredients for selected seeded days.
- Do not create `premium_shopping_items`, `user_premium_shopping_checks`, or any shopping source-of-truth table.
