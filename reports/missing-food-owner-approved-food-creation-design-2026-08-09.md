## Current Contract

Missing Food Drafts are now production-smoke-passed:

- `public.food_missing_food_drafts` exists.
- A draft can reach `status = 'ready_for_owner_apply'`.
- Draft rows preserve nutrition/provenance fields.
- `applied_food_id`, `applied_by`, and `applied_at` remain empty until a separate owner-approved creation step exists.

Food Core runtime/type contract includes:

- `id`
- `stable_food_id`
- `name`
- `normalized_name`
- `category`
- `source`
- `calories`
- `protein`
- `fat`
- `carbs`
- `fiber`
- `unit`
- `brand`
- `barcode`
- `verified`
- `created_by_user_id`
- `canonical_food_id`
- `source_version`

Existing write paths are not suitable as-is for Missing Food creation:

- user-created foods are private `source = 'user'`;
- ingestion/import paths can upsert many foods, create aliases, and recompute dependent data;
- Missing Food creation must be a small separate owner-approved path that creates exactly reviewed core foods and does not create aliases.

## Proposed Flow

1. Admin prepares a missing-food draft.
2. Draft reaches `ready_for_owner_apply`.
3. Owner selects exactly one draft id for apply.
4. Owner runs pre-checks against the selected draft and current Food Core.
5. Owner-approved apply creates exactly one `public.foods` row.
6. The same transaction marks the draft `applied`.
7. Post-check proves only the intended `foods` row and draft tracking changed.
8. Any alias for the original query is handled later through Admin-approved Alias Apply.

This should be implemented later as either:

- a reviewed security-definer RPC with strict validation; or
- a one-off owner apply package for exactly selected draft ids.

Do not use the existing import/ingestion commit path for this workflow.

## Required Pre-Apply Validations

Selected draft:

- draft exists by explicit `draft_id`;
- `status = 'ready_for_owner_apply'`;
- `applied_food_id`, `applied_by`, and `applied_at` are all null;
- `source_review_id` points to `food_missing_review_queue`;
- source review classification is `missing_canonical_food`;
- source review status is `approved_for_food_draft`;
- `name`, `normalized_name`, `category`, and `data_source` are non-blank;
- `normalized_name = public.normalize_food_text(name)`;
- `source = 'core'`;
- `unit = 'g'`;
- `brand` is null;
- `barcode` is null for the MVP.

Duplicate/canonical checks:

- no existing shared food has the same exact `normalized_name` with empty/null normalized brand;
- no existing canonical food already represents the same food;
- no conflicting `stable_food_id`, if one will be assigned;
- no existing alias already resolves the draft query to a canonical food in a way that makes a new food unnecessary.

Nutrition/provenance checks:

- calories, protein, fat, and carbs are present, finite, and non-negative;
- values remain inside the DB draft bounds;
- fiber is either null or finite/non-negative;
- unknown fiber must remain `null`, not silently become `0`;
- `data_source` is present;
- `source_notes` or `reviewer_notes` should explain manual or external provenance;
- all-zero nutrition requires an explicit reviewer note.

Schema/dependency checks:

- `public.foods.id` is uuid/defaultable;
- `public.foods.normalized_name` exists;
- `public.foods.source` allows `core`;
- `public.foods.unit` supports `g`;
- production `foods.fiber` supports the intended nullable-fiber semantics;
- `public.foods.canonical_food_id` exists or the approved fallback is documented;
- existing trigger/function behavior for self-root canonical ids is known before apply;
- `public.user_profiles.id_user` and admin identity checks remain production-correct if an RPC is used.

Stop if any validation fails.

## Expected Food Insert Shape

The future apply should insert one `public.foods` row with this shape:

| Field | Expected value |
| --- | --- |
| `id` | generated uuid, captured as `new_food_id` |
| `stable_food_id` | optional; assign only if production column exists and stable-id semantics are approved |
| `name` | draft `name` |
| `normalized_name` | draft `normalized_name` or generated by the existing normalize trigger |
| `category` | draft `category` |
| `source` | `core` |
| `calories` | draft `calories` |
| `protein` | draft `protein` |
| `fat` | draft `fat` |
| `carbs` | draft `carbs` |
| `fiber` | draft `fiber`, preserving `null` |
| `unit` | `g` |
| `brand` | null |
| `barcode` | null |
| `verified` | true, if owner approves this as Food Core |
| `created_by_user_id` | null |
| `canonical_food_id` | self-root, equal to inserted `id` |
| `source_version` | optional provenance/version marker only if semantically approved |

Canonical self-root can be achieved by:

- relying on the existing `foods` trigger if production confirms it sets `canonical_food_id = id` when null; or
- a reviewed two-step transaction that inserts the row, then sets `canonical_food_id = id`.

The chosen mechanism must be explicit in the future apply package.

## Draft Apply Tracking

After successful food insert, the same transaction should update only the selected draft:

- `status = 'applied'`;
- `applied_food_id = new_food_id`;
- `applied_by = auth.uid()` or explicit owner/admin id;
- `applied_at = now()`;
- `updated_at` updated by the draft trigger.

The draft should not be marked applied unless the food insert succeeded.

## Post-Apply Validation

Expected post-checks:

- `foods` count increased by exactly `+1`;
- the inserted food exists by returned `id`;
- inserted food has `source = 'core'`;
- inserted food has `unit = 'g'`;
- inserted food has `canonical_food_id = id`;
- inserted food has expected name, normalized name, category, nutrition, and nullable fiber;
- `food_aliases` count is unchanged;
- `food_alias_apply_audit` count is unchanged;
- selected draft is `applied`;
- selected draft `applied_food_id`, `applied_by`, and `applied_at` are filled;
- all non-selected draft rows are unchanged;
- `food_missing_review_queue` count is unchanged;
- `food_search_events` and `food_search_review_queue` counts are unchanged;
- diary/favorites/recipes counts are unchanged;
- no import/backfill/recompute was run.

## Alias Follow-Up

No alias should be created automatically.

After the new canonical food exists, the original query may be reviewed as a separate alias candidate only if:

- it is still a safe alias for exactly that canonical food;
- it has source event evidence;
- it is not ambiguous/manual/noise;
- duplicate/conflict checks pass.

That follow-up must use the existing Admin-approved Alias Apply flow or a separately reviewed owner package. It must not be a side effect of food creation.

The owner-approved food creation workflow is designed and ready for a separate DB/RPC or owner apply draft. The future workflow must create exactly one reviewed `core` food from a `ready_for_owner_apply` draft, mark that draft applied, preserve nullable fiber semantics, and leave aliases plus all dependent user data unchanged.
