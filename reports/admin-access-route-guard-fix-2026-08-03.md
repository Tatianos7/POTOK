## Audit Finding

Admin access was derived only from `AuthContext.user.isAdmin` / `profile.is_admin` inside the pages.

Risk:

- `profileService.getProfile(...)` can return a cache/default fallback with `is_admin = false` after a transient profile read issue.
- Once `authStatus = authenticated`, both admin pages immediately redirected on `!user?.isAdmin`.
- This caused a real admin session to be redirected back into the app before a production `user_profiles.id_user` admin check could confirm access.

Production schema note:

- Production admin profile identity uses `public.user_profiles.id_user`.
- The route fix explicitly checks `id_user = current auth user id`.
- A `user_id` fallback exists only for schema compatibility and is not the production path.

## Implemented Fix

Added:

- `src/services/adminAccessService.ts`
- `src/hooks/useAdminAccess.ts`

Updated:

- `src/pages/AdminPanel.tsx`
- `src/pages/SearchAnalyticsAdminReview.tsx`

Behavior:

- If local auth/profile context already confirms admin, access is allowed immediately.
- If authenticated context says non-admin/fallback, admin pages enter `checking` and run a direct read:
  - `user_profiles.select('is_admin').eq('id_user', user.id).maybeSingle()`
- Redirect to `/` happens only after the remote admin check returns denied.
- Both `/admin` and `/admin/search-review` now share the same guard behavior.
- GitHub Pages nested route fallback remains unchanged.

## Route Review

`/admin`:

- Protected first by `ProtectedRoute`.
- Then checked by `useAdminAccess`.
- Loads admin panel data only when `adminAccessStatus = allowed`.

`/admin/search-review`:

- Protected first by `ProtectedRoute`.
- Then checked by `useAdminAccess`.
- Loads Search Review items only when `adminAccessStatus = allowed`.

This keeps non-admin users blocked while avoiding premature redirect for admin sessions whose profile/admin flag is still being verified.
