## Implemented

- Added `src/services/aliasApplyService.ts`.
- `aliasApplyService.applyApprovedAlias(...)` calls only:
  - `public.apply_admin_approved_food_alias(p_review_id, p_alias, p_comment)`.
- The service maps RPC rows into runtime-safe shape:
  - `result`;
  - `aliasId`;
  - `error`.
- Blank alias/comment input is sent as `null`, so the DB/RPC contract can fall back to the approved review query.
- No direct runtime writes to `food_aliases` or `foods` were added.

## Admin UI

- `/admin/search-review` now shows existing queue rows for the reviewed search item, including approved rows.
- Status buttons remain available only for `pending` rows.
- `Apply alias` is shown only for approved queue rows.
- The apply action is explicit and admin-click-only.
- Already-applied rows display their applied alias id and cannot be applied again from the UI.
- After apply, the page reloads queue state so `applied_alias_id`, `alias_apply_result`, and `alias_apply_error` are visible.

Displayed RPC results:

- `duplicate_alias`
- `existing_alias_conflict`

- `ambiguous_alias`

- `invalid_alias`
- `review_not_found`
- `insert_failed`
